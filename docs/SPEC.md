# 全国避難所リスク可視化サービス 仕様書 v0.2

v0.1 からの主な変更：読み取り系データを Supabase から外し、Cloudflare R2 上の静的ファイル（PMTiles / JSON）配信に変更。固定費ゼロ（ドメイン代を除く）で運用する。

---

## 0. 設計思想（実装判断の拠り所。削らないこと）

### 0.1 このサービスが可視化するもの

このサービスは「どの避難所が危険か」を判定するものではない。可視化するのは次の2つ。

1. 公的データが持っている情報と、避難生活に必要な情報とのギャップ
2. そのギャップを埋めた結果として見えてくる、平時の整備不足

したがって **「未確認（unknown）」を第一級の状態として扱う。** 情報が欠けている避難所を灰色で大量に表示すること自体が、このサービスの最も強いメッセージになる。欠損値を推定値で埋めて地図を「きれいに」してはならない。

### 0.2 訴求の根拠となる実データ

- 公立小中学校の普通教室の空調設置率：99.6%
- 同じ学校の体育館等の空調設置率：31.7%（文部科学省、令和8年5月1日現在調査、2026年7月30日公表）
- 政府は第1次国土強靱化実施中期計画で、避難所となる体育館等の空調設置率を2035年度までに100%とする目標を掲げている

「授業を受ける教室にはエアコンがあるが、被災者が寝泊まりする同じ学校の体育館にはない」。この非対称性がコアメッセージ。

### 0.3 法的・倫理的な制約（必ず守る）

- 特定の避難所を「危険」と断定表示しない。表示するのは観測された事実と、その事実が示す不足。文言は「未確認」「要確認」を使う。
- 平常時の啓発ツールであり、災害時の避難誘導には使わせない。全ページ最上部に公式情報への誘導バナーを出す（§6.6）。
- 自治体名指しのランキングは作らない。集計は都道府県単位まで。
- 市民投稿には施設管理者からの訂正・削除要請フローを用意する（§4.5）。

## 2. データ設計

### 2.1 最重要の前提：「指定緊急避難場所」と「指定避難所」は別物

災害対策基本法 第49条の4 / 第49条の7 に基づく別々の指定。

| | 指定緊急避難場所 | 指定避難所 |
|---|---|---|
| 目的 | 命を守るために緊急に逃げ込む場所 | 被災者が一定期間生活する施設 |
| 例 | 高台、公園、津波避難タワー、学校の校庭 | 体育館、公民館 |
| 指定単位 | 災害種別ごと（洪水 / 崖崩れ・土石流・地滑り / 高潮 / 地震 / 津波 / 大規模な火事 / 内水氾濫 / 火山現象 の8種） | 種別区分なし |
| 本サービスでの扱い | ハザード適合性（軸A）の評価対象 | 設備・収容力（軸B/C/D）の主対象 |

同一の物理施設が両方に指定されていることが多い。データ上は **施設（facility）1件に、指定（designation）を種別ごとの配列で持つ**。同じ施設に同じ種別の行が複数ある（建物と校庭、一般の避難所と受入対象者を限定した避難所など）ため、行は畳まない（`docs/DATA_NOTES.md` D-12）。

### 2.4 静的ファイルの構成（R2）

```
/tiles/shelters.pmtiles                 全施設の点データ
/facilities/by-muni/{muni_key}.json     市区町村ごとの施設詳細
/summary/national.json                  全国集計
/summary/munis.json                     都道府県→市区町村の索引（リスト表示用。地図の初期表示では読まない）
/summary/pref/{pref_code}.json          都道府県集計（Phase 5）
/summary/evacuee-estimates.json         都道府県の被害想定による市区町村別の避難者数（§3.3）
/geocode/{pref_code}.json               住所照合用の町丁目の代表点（§6.6）
/points/{lat}_{lng}.json                緯度経度 1 度ごとの施設の位置と要約（§6.6）
/meta.json                              生成日時、D1 の取得日、件数、スキーマバージョン
```

**タイルの属性（最小限に保つ）**

| 属性 | 型 | 内容 |
|---|---|---|
| `id` | string | facility_id |
| `name` | string | 施設名 |
| `muni` | string | muni_key |
| `kind` | int | ビットフラグ。1=指定緊急避難場所、2=指定避難所 |
| `hz` | int | 災害種別8種のビットマスク（指定緊急避難場所のみ） |
| `state` | string | display_state（§3.6） |
| `ac` | string | `aircon_main_hall` の確定値。未確認・争点中なら属性自体を持たない |
| `acn` | int | 冷房なし（`ac` が `none`）なら 1。まとめ表示では合算値 |
| `s0`〜`s4` | int | 表示状態（unknown / critical / poor / fair / good の順）に該当すれば 1。まとめ表示では合算値 |
| `rs` | int | 避難所の指定がすべて受入対象者限定なら 1、それ以外は 0 |
| `ne` / `ns` | int | 指定緊急避難場所／指定避難所の指定があれば 1。まとめ表示では合算値 |
| `h0`〜`h7` | int | 災害種別ごとの指定があれば 1（順序は `hz` のビットと同じ）。まとめ表示では合算値 |

`ne` / `ns` / `h0`〜`h7` / `s0`〜`s4` / `acn` は、低ズームのまとめ表示で絞り込み中の件数を出すためのもの。絞り込みの条件が 1 つまでなら合算値が正確な件数になる。条件が 2 つ以上重なると合算値からは求められないため、まとめ表示には件数を出さず、印だけを表示して拡大を促す（個別の点は正確に絞り込む）。まとめ表示の印は表示状態にかかわらずグレーとし、色を付けるのは個別の点だけ（2026-11-15 決定）。

タイルの要件：低ズームではクラスタ表示（件数付き）、z12 以上で全点を個別表示。tippecanoe で生成する。フラグの具体値は実装時に決めてよいが、点の間引きで施設が消えないこと。

### 2.5 ID体系・重複統合（Step 0 の結果で確定）

次の3点は実データを見るまで決めない。Step 0（§9）で調査し、`docs/DATA_NOTES.md` に決定内容を記録する。

- `facility_id`：再取り込みしても変わらない安定IDであること（市民投稿が紐づくため）
- `muni_key`：市区町村を一意に表すキー。全国地方公共団体コードを導出できるならそれを使う
- 2つのCSVに現れる同一施設の統合規則。**曖昧なものは統合せず、`data/build/merge_candidates.json` に出力して人手判断に回す**

### 2.7 Supabase スキーマ（Phase 2）

施設本体は Supabase に持たない。参照整合性のために最小限の索引テーブルだけ同期する。

```sql
-- ビルドスクリプトが同期する施設索引（投稿先の存在確認用）
create table facility_index (
  facility_id text primary key,
  muni_key    text not null,
  name        text not null,
  deprecated_at timestamptz
);

-- config/amenity-defs.json から同期
create table amenity_defs (
  key text primary key,
  value_type text not null,
  enum_options jsonb
);

-- 確定値（原本）
create table facility_amenities (
  facility_id text references facility_index(facility_id),
  amenity_key text references amenity_defs(key),
  value jsonb not null,
  confidence text not null check (confidence in ('official','verified','reported','disputed')),
  evidence_count int not null default 0,
  observed_at date,
  last_report_id uuid,
  updated_at timestamptz default now(),
  primary key (facility_id, amenity_key)
);

-- 市民投稿（不変ログ）
create table reports (
  id uuid primary key default gen_random_uuid(),
  facility_id text not null references facility_index(facility_id),
  amenity_key text not null references amenity_defs(key),
  value jsonb not null,
  basis text not null check (basis in ('official_doc','on_site','photo','hearsay')),
  source_url text,
  photo_urls text[],
  observed_at date not null,
  note text,
  reporter_id uuid not null references auth.users(id),
  -- 投稿時点の投稿者の立場。施設管理者の投稿は official として扱う
  reporter_role text not null default 'user' check (reporter_role in ('user','facility_admin')),
  status text not null default 'pending'
    check (status in ('pending','accepted','rejected','superseded')),
  reviewed_by uuid references auth.users(id),
  reviewed_at timestamptz,
  reject_reason text,
  created_at timestamptz default now()
);
create index on reports (facility_id, amenity_key, status);

-- 異議申し立て
create table disputes (
  id uuid primary key default gen_random_uuid(),
  facility_id text not null references facility_index(facility_id),
  amenity_key text not null references amenity_defs(key),
  reason text not null,
  counter_value jsonb,
  evidence_url text,
  raiser_id uuid not null references auth.users(id),
  status text not null default 'open' check (status in ('open','resolved','dismissed')),
  resolution_note text,
  resolved_by uuid references auth.users(id),
  resolved_at timestamptz,
  created_at timestamptz default now()
);
```

上記のほかに、次を持つ（定義の正は `supabase/migrations/`）。

- `facility_admin_applications`：施設管理者アカウントの申請（§4.5）。本人とモデレーターだけが読める。
- `removal_requests`：削除・訂正の要請（§4.5）。モデレーターだけが読める。
- `private.settings`：公開しない設定値。`auto_accept_new_with_evidence`（§4.2 の自動承認の切り替え。初期値は無効）、投稿者を匿名化するための塩、投稿写真の URL の接頭辞。
- 公開ビュー `reports_public` / `disputes_public`（§4.4）と、モデレーション用のビュー。

## 3. リスク評価ロジック（4軸）

スコアは DB ではなく**ビルドスクリプト（TypeScript）で算出**し、静的ファイルに書き出す。

### 3.1 基本原則

- 各軸は 0〜100。算出に必要な入力が欠けている軸は `null`（未評価）。0 や平均値で埋めない。
- 総合点（単一の数値）は作らない。表示は常に4軸。設備（軸C）は点数ではなく、観点ごとの状態で示す（3.4）。
- `breakdown` に中間値と `method_version` をすべて保存し、詳細ページで開示する。

### 3.2 軸A：ハザード適合性（Phase 4）

指定されている災害種別について、その地点の想定ハザード（D5）と矛盾がないかを見る。

```
mismatch = 「その災害種別の指定緊急避難場所」かつ「その災害の想定区域内」
```

**軸A は点数を出さない**（2026-11-15 決定。当初案の `score_hazard = 100 − (mismatch数 ÷ 指定種別数 × 100)` は採らない）。

- ハザードのデータ（D5）には未整備の場所があり、タイルに色がない地点を「想定区域外」と断定できない。色がない地点を「問題なし」として満点にすると、欠損を「問題なし」で埋めることになる。
- 表示は 3 通り。mismatch が 1 つでもあれば「要確認の種別がある」（該当する災害種別を並べる）。確認できた種別に mismatch がなければ「確認できる範囲では重なりなし」（「適合」や 100 点とは表示しない）。データで確認できない種別（地震・大規模な火事・火山現象）しか指定がなければ「未評価」。
- `scores.hazard` は常に `null`。結果は `scores.hazard_check` に、確認した種別・重なりがあった種別・確認できない種別を分けて持つ。

mismatch は指定の誤りを意味しない（垂直避難が前提の場合など）。画面上は「要確認」と表示する。詳細ページには「最新かつ詳細な情報は各市町村が作成するハザードマップをご確認ください」と出典（「ハザードマップポータルサイト」を加工して作成）を必ず出す。

### 3.3 軸B：収容余力（Phase 4）

**点数は出さない**（2026-11-15 決定。`docs/DATA_NOTES.md` 12.7、D-22）。自治体の公開データに有効面積がなく、想定収容人数の算出の前提も自治体ごとに違うため。`scores.capacity` は常に `null`。

- 想定収容人数（`capacity_persons`）を参考として表示する。
- 自治体が公表している想定収容人数（D3）は、指定ごとに `designations.*[].capacity` として持ち、出典を添えて表示する。市民投稿の `capacity_persons` とは混ぜない（`docs/DATA_NOTES.md` 12.13、D-28）。
- 有効面積（`capacity_area_sqm`）と想定収容人数の両方がそろった施設にだけ、1 人あたり面積（有効面積 ÷ 想定収容人数）を参考値として出す。参照線：2.0㎡（国内の従来想定）／ 3.5㎡（スフィア基準）。
- トイレは `toilet_total` に対しスフィア基準（20人に1基）を参照線として併記する。
- 避難者の規模の参考として、都道府県の地震被害想定で公表されている市区町村別の避難者数を、出典付きで市区町村のページに引用する。本サービス独自の推定は行わない。点数・表示状態には使わない（`docs/DATA_NOTES.md` D-32）。

### 3.4 軸C：設備の評価（2026-11-21 改定。`docs/DATA_NOTES.md` 16.3）

点数の足し算をやめ、設備ごとに「災害時に何に影響するか」で 4 つの観点に分けて、観点ごとの状態を示す。

| 観点 | key | 内容 |
|---|---|---|
| 命にかかわる | `life` | 欠けると災害関連死につながる経路が公的資料で示されている設備（冷房・暖房・トイレの数・断水時のトイレ・給水・非常用電源・太陽光＋蓄電池・簡易ベッド） |
| 健康 | `health` | 断熱・入浴・敷地内備蓄・調理設備 |
| 尊厳・プライバシー・安全 | `dignity` | 間仕切り・男女別の更衣室と授乳室・トイレまでの照明と防犯・Wi-Fi・ペット |
| 使えるかどうか（高齢者・障害者） | `access` | 洋式化・多目的トイレ・段差・エレベーター |

- 各項目の観点・季節・判定規則・根拠は `config/amenity-defs.json` の `impact`・`season`・`status_rule`・`impact_basis_ja` に持つ。`impact` が null の項目（自立運転時間・備蓄日数・収容人数・面積）は参考値で、判定に使わない。
- 項目の状態は「不足・一部・充足・判定に数えない・未確認」。未確認の値を「なし」として扱わない。`confidence='disputed'` は未確認として扱う。
  - 例：冷房・暖房は「なし」が不足、「スポットのみ」「一部」が一部、「全体」「あり（範囲は未確認）」が充足。
  - 非常用発電機がなくても、太陽光＋蓄電池があれば不足にしない（一部）。
  - エレベーターと太陽光＋蓄電池は、ないことだけでは判定に数えない。
  - トイレの数は、想定収容人数とそろったときだけ判定する（50 人に 1 基。スフィア基準・内閣府トイレガイドライン）。
- 観点の状態：1 つでも不足があれば不足（他の項目の充足で打ち消さない）。判定に数える項目がすべて確認済みなら充足または一部。確認できていない項目が残れば未確認。
- 冷房（夏）・暖房（冬）のように重さが季節で変わる項目は、表示状態を季節で変えず、画面で季節を明示する。
- `coverage_ratio` は確認済みの項目数 ÷ 全項目数の参考値で、表示状態には使わない。

### 3.5 軸D：到達性・兵站（Phase 4）

v1 は単純指標で開始する：緊急輸送道路までの直線距離（500m未満=100 / 2km未満=70 / 5km未満=40 / それ以上=10）、敷地内備蓄の有無で±20。

- 対象は指定避難所の指定がある施設。それ以外は `null`（未評価）。
- 20km 以内に緊急輸送道路の指定が見つからない施設（離島など）も `null`（未評価）。いちばん低い点数にはしない（D-26）。
- 5km 以上離れている施設は、行政区域データ（N03）で「ひと続きの陸地」を調べ、同じ陸地に緊急輸送道路の指定が 1 本もなければ `null`（未評価）にする（D-29）。
- 道路は国土数値情報 緊急輸送道路（N10、非商用）。高速自動車国道と都市高速道路は距離の計算から除く。
- 敷地内備蓄が未確認なら、加点も減点もしない。結果は 0〜100 に収める。
- 直線距離であること、最寄りの道路の名称・区分、もとの資料の年月を詳細ページに出す（`docs/DATA_NOTES.md` 12.6、D-24）。

### 3.6 表示状態（2026-11-21 改定）

| display_state | 色 | 条件 |
|---|---|---|
| `critical` | 赤 | 命にかかわる設備の不足が確定している。または、命にかかわる設備がすべて確認済みで、軸A に重なりがある |
| `poor` | オレンジ | 健康・尊厳・使いやすさの観点で不足が確定している |
| `unknown` | グレー（無視されない濃さ） | 上に当たらず、命にかかわる設備に未確認のものが残る |
| `fair` | 黄 | 命にかかわる設備がすべて確認済みで、不足がない |
| `good` | 緑 | 4 観点すべて充足、軸A を確認済みで重なりなし、軸D が 75 以上 |

軸D（緊急輸送道路までの距離）は立地の条件で、施設の不備ではないので、`good` の条件にだけ使う（`docs/DATA_NOTES.md` D-30）。
軸A の重なりだけで設備が分からない施設は `unknown` のまま（地図では三角の印で示す）。

色だけに頼らず、マーカー内の記号を併用する。凡例は常時表示。

## 4. 市民投稿と検証（Phase 2）

### 4.1 信頼度

| confidence | 条件 |
|---|---|
| `official` | 自治体公開データ、または施設管理者アカウントの投稿（担当の市区町村の施設に限る。§4.5） |
| `verified` | 異なる2名以上が、根拠 `on_site` または `photo` で同じ値を投稿し、観測日が180日以内 |
| `reported` | 投稿1件のみ、またはモデレーター承認 |
| `disputed` | 未解決の異議がある。スコア計算から除外し、詳細ページに注記 |

### 4.2 投稿フロー

1. 閲覧は匿名可。投稿はログイン必須（Supabase Auth）。**開始時は Google ログインのみ**（2026-11-14 決定）。メールのマジックリンクは、メール送信サービスを用意してから追加する（Supabase 標準のメール送信は本番利用に向かないため）。
2. 根拠（basis）と観測日（observed_at）は必須。`official_doc` は URL 必須、`photo` は写真1枚以上必須。
3. 投稿は `pending` で保存。
4. 自動処理（Supabase の Postgres 関数。投稿時に実行）：
   - 確定値と一致 → `accepted`、evidence_count を加算
   - 確定値と矛盾 → `pending` のままモデレーション待ち
   - それ以外 → すべてモデレーション待ち
   - **開始時は「確定値と一致」だけを自動承認とする**（2026-11-14 決定、§10-4）。当初案の「確定値なし、かつ根拠が `official_doc` / `photo` → 自動で `accepted`（confidence=`reported`）」は、投稿の質が分かってから有効にするかを判断する。有効・無効を設定で切り替えられる形で実装する。
5. モデレーターが承認・却下。却下理由は記録され、履歴として公開される。

### 4.3 反映の経路

- 詳細ページは、静的JSONの確定値に加えて、Supabase から当該施設の最新の `facility_amenities` を取得して上書き表示する（取得に失敗しても静的値で表示を続ける）。
- 地図タイルとスコアへの反映は次回ビルド時（日次）。詳細ページに「地図への反映は最大1日かかります」と明記する。

### 4.4 誤情報の訂正

- すべての設備値の横に「この情報は違う」を常設。
- 押すと `disputes` が作られ、その項目は即座に `disputed` になる。濫用防止のため1ユーザーあたり24時間で3件まで。
- 争点は自由記述の議論にせず、「対立する2つの値」として並べて表示する。異議の理由の自由記述と根拠 URL は公開せず、モデレーターだけが読む。公開するのは対立する値・状態・運営の判断。
- モデレーターは異議を「解決」とする際に、確定値を取り下げて「未確認」に戻せる（支えていた投稿は `superseded` になり、消えない）。正しい値は新しい投稿で入れ直す。
- `reports` は物理削除しない（DELETE と TRUNCATE をデータベース側で禁止する）。施設ごとの編集履歴を誰でも閲覧できる。
- 公開する履歴の範囲：投稿の補足（自由記述）・根拠 URL・写真は、承認済み（および後の情報で置き換えられたもの）だけ公開する。確認待ち・却下の投稿は、項目・値・根拠の種類・状態・却下理由だけを公開する（未確認の文章やリンクが確認前に公開されるのを防ぐため）。
- 投稿者は、利用者 ID から作った 10 文字の記号で表示する。同じ人の投稿は同じ記号になるが、記号から利用者は特定できない。

### 4.5 荒らし対策・施設管理者

- 新規アカウントは登録後24時間、投稿3件まで。それ以降も、1利用者あたり24時間で100件まで。
- 却下率が50%を超えたアカウントに要注意フラグ。フラグはモデレーション画面に表示するだけで、投稿の自動制限は行わない。
- 写真はアップロード時にサーバー側（Supabase Edge Function）で EXIF を除去・リサイズしてから R2 に保存する。除去前のファイルは公開しない。
- 施設管理者アカウント：申請制（`lg.jp` ドメイン等の確認＋手動承認）。承認時に担当の市区町村を付け（`app_metadata.muni_keys`）、**その市区町村の施設への投稿だけ**を `official` として即時反映する。担当外の施設への投稿は一般の利用者と同じ扱い。訂正はできるが履歴は消せない。
- 削除要請フォームを別途用意し、運営が判断する。ログインなしで出せ、内容は運営だけが読む。

## 6. 画面仕様

### 6.1 `/` 地図（Phase 1）

- 全画面地図。フィルタパネル（PCは左、モバイルは下部シート）。
- フィルタ：指定種別、災害種別、表示状態。Phase 3 で設備フィルタを追加し、**「冷房なしだけを表示」をワンタップで実行できる**ようにする。

- ヘッダーに全国サマリー（掲載件数、設備情報が1項目以上ある施設の件数と割合）。割合の低さを隠さない。
- マーカーを選ぶと要約カード（施設名、指定種別、表示状態）を出し、詳細ページへ遷移できる。
- 受入対象者を限定した避難所（避難所の指定がすべて限定の施設）は、地図では白抜きの印、要約カードとリストでは「受入対象者限定」のラベルで区別する。詳細ページでは枠付きで「受入対象者が限定されています」と `受入対象者` の原文を出す。絞り込みの項目には加えない。
- 「指定避難所 × 災害種別」で絞り込んでいる間は、まとめ表示に件数を出さない旨を案内する（§2.4）。
- 指定された災害の想定区域と地点が重なる施設（軸A が「要確認」）は、表示状態の色とは別に、印の右上に黒い三角に白い「!」の印を重ねる。設備の回答率に関係なく出す。まとめ表示には付けない。凡例で「指定の誤りを意味するものではない」と説明する。絞り込み「想定区域と重なる施設だけを表示」をワンタップで実行できるようにする（`docs/DATA_NOTES.md` D-35）。
- 全国地図と施設詳細の地図に、ハザードマップポータルサイトの表示用タイル（洪水・土砂災害・津波・高潮）を 1 つ選んで重ねられる。初期状態は「重ねない」。施設の印より下に描き、地図の出典に「ハザードマップポータルサイト」を加える。重ねている間は「色が付いていない場所も安全とは限らない」「最新の詳しい情報は市区町村のハザードマップで確認する」旨と、凡例へのリンクを出す。タイルは利用者の端末が直接読み込む（`docs/DATA_NOTES.md` D-36）。
- 地図の上に検索窓を置く（住所・地名）。都道府県名は省略でき、市区町村名から都道府県を決める（同じ名前の市が複数あるときは選ばせる）。照合は §6.6 と同じく端末の中だけで行い、見つかった地点に印を置いて移動する。
- 最後に見ていた地図の位置（ズーム 8 以上のとき）を端末のブラウザ内に保存し、次に開いたときはそこから表示する。保存がなければ「住所から探す」で保存した場所、それもなければ全国を表示する。
- スマホでは地図を画面の高さいっぱいに取り、絞り込み・凡例・ハザードマップの選択は検索窓の横の「絞り込み」ボタンで開閉する（初期は閉じる）。閉じている間も、凡例は地図の左下に小さく出す（`docs/DATA_NOTES.md` D-37）。
- スマホ（幅 640px 未満）では、上のナビの代わりに画面下に固定のメニュー（地図／近くを探す／一覧）を出す。PC は上のナビのまま。一覧の最初の画面は地方（北海道・東北・関東・中部・近畿・中国・四国・九州・沖縄）で分け、開いた地方の都道府県を出す（`docs/DATA_NOTES.md` D-38）。
- 地図の色分けを切り替えられる：設備の状況（表示状態）／洪水・津波・高潮の浸水深／土砂災害の区域／緊急輸送道路までの距離。指標で色分けしている間は、まとめ表示をやめて全施設を小さな点で描き、全国を見ても分布が分かるようにする。分からない施設は灰色で「データなし・未確認」。初期は「洪水の浸水深」（設備の情報がほぼ公表されていないため）。浸水深・土砂の色はハザードマップポータルサイトの凡例の色に合わせる（`docs/DATA_NOTES.md` D-39）。
- 施設詳細に「この地点の想定（浸水深・土砂災害）」を出す。市区町村の一覧に、指定避難所の数と、そのうち地点の想定浸水深 3m 以上・土砂災害の区域内の数を出し、多い順にも並べられる（D-39）。
- 地図画面は情報を絞る：上は検索（角丸の 1 本の入力欄と、設定ボタン）と色分けの切り替えだけ。検索は入力に合わせて候補を出す（市区町村名の一部一致、市区町村を決めた後は町名の前方一致）。拡大・縮小ボタンは右下に置き、タッチ端末では出さない。絞り込み・凡例・ハザードマップ・全国の概況（スマホ）は設定ボタンで開くパネルにまとめ、長い説明は「この色について」に畳む。避難所を選ぶと、スマホは下から大きなカード（名前、地点の浸水深などの要点、「施設の詳細を見る」）を出す。PC は右上に出す（`docs/DATA_NOTES.md` D-40）。

### 6.2 `/f/{muni_key}/{facility_id}` 施設詳細（Phase 1）

- 施設名、住所、小さな地図、経路を開く外部リンク
- 指定種別と対応災害種別のバッジ
- 4軸のスコア（水平バー4本。未評価は「未評価」と表示し、バーを空にしない＝0点に見せない）
- 設備チェックリスト（カテゴリ別。未確認の項目も「未確認」として全項目を並べる）
- スコア根拠の開示（折りたたみ）
- 出典、データ取得日、「最新かつ詳細の状況は当該市町村にご確認ください」の注記
- Phase 2 で「情報を追加」「この情報は違う」「編集履歴」を追加
- 備蓄の数（2026-11-24 追加）：避難所ごとの資料（D9）があれば「この避難所の備蓄」を出す。市区町村全体の数（D8）は折りたたんで出す。項目は `config/stockpile-defs.json` から作り、資料に記載のない項目は出さない（0 と書かない）

### 6.3 `/list` リスト表示（Phase 1）

地図に依存しない一覧。都道府県→市区町村→施設の順にたどれる。スクリーンリーダーと低スペック端末のための代替経路。

市区町村の施設一覧には「市区町村全体の備蓄」（D8）を出す（2026-11-24 追加）。市区町村の合計であること、どの避難所にあるかは分からないこと、協定による調達を含まないことを必ず併記する。市区町村を並べて順位を付けることはしない。その後に県が公表した数（D10）があれば「その後の公表との比べ」を出す（2026-11-24 追加）。品目ごとに 2 つの数と違いを出し、3 倍以上・3 分の 1 以下・0 をまたぐ違いは「要確認」とする（DATA_NOTES 20）。

### 6.4 投稿・モデレーション（Phase 2）

- `/f/{muni_key}/{facility_id}/report`：1画面1項目のステップ形式。現地で目視確認しやすい項目から並べる。
- `/moderation`：投稿の承認待ち、異議、施設管理者申請（要権限）。

### 6.5 `/pref/{code}` 都道府県サマリー、`/about`、`/data`（Phase 5）

- 件数、表示状態の構成比、設備別の充足率。D7 の体育館空調設置率を並置。
- `/data`：集計データのダウンロード（CC BY 4.0。ただし緊急輸送道路に関する項目は非商用に限る。§8）。
- `/about`：趣旨、評価方法、出典、運営者、問い合わせ・削除要請。

### 6.6 `/near` 住所から近くの避難所を探す（追加機能、2026-11-19 決定）

利用者が自分や親族の住所を入力して、近くの指定緊急避難場所・指定避難所を調べる。`docs/DATA_NOTES.md` 13 章、D-33・D-34。

- **住所は端末の外に出さない。** 都道府県を選んで住所を入力すると、端末はその都道府県の照合用ファイル（`geocode/{都道府県コード}.json`）だけを取得し、端末の中で町丁目の代表点に照合する。本サービスにも外部のサービスにも住所を送らない。
- 照合の候補が 1 つに決まらないときは候補の一覧から選んでもらう。照合できないときは地図で地点を選んでもらう。
- 照合した位置を地図に示し、利用者が確認する。地図をタップして位置を直せる。位置の精度は町丁目単位（農村部では 1km 以上ずれることがある）であることを明記する。
- 近くの施設は、選んだ地点から直線距離で 3km 以内を近い順に示す。3km 以内にない場合は最寄りの 5 か所を示す。施設の位置は、緯度経度 1 度ごとに分けたファイル（`points/{緯度}_{経度}.json`）から読む（地点の周辺の区画だけを取得する）。
- 各施設には、指定の種類、災害種別、表示状態、想定区域との重なり（軸A）、受入対象者の限定を出し、詳細ページへリンクする。その市区町村の想定避難者数（§3.3）へもリンクする。
- 文言は「近くの指定避難所」にとどめ、「あなたの避難先」とは書かない。自治体の公式情報（ハザードマップ、地区ごとの避難先）を確認するよう案内する。直線距離であり、川・線路・崖などは考慮していないことを明記する。
- 入力した地点が想定区域に入っているかは、本サービスでは調べない。「重ねるハザードマップで確認する」リンクを置き、押したときだけ位置を渡す。
- 保存は既定でしない。利用者が選んだ場合だけ、呼び名（「自宅」「実家」など）と確認済みの位置（座標）を、その端末のブラウザ内に保存する。住所の文字列は保存しない。保存した地点は消せる。アカウントへの保存、端末間の同期、位置を含む共有用 URL は作らない。
- 照合用データは国土交通省「位置参照情報」（大字・町丁目レベル）。出典を画面に表示する。

### 6.6.1 `/inquiries` 照会の記録（2026-11-21 追加。`docs/INQUIRY.md`）

- 自治体への照会の目的、照会先の選び方（条件と出典）、依頼している内容を示す。
- 照会先の候補と記録がある市町村を、都道府県ごとに並べ、状況（まだ照会していない／回答待ち／回答あり／資料なし など）と経過（日付・種類・要旨・資料名）を出す。自治体の順位や点数は出さない。
- 市町村の施設一覧ページ（`/list/{pref}/{muni}`）に「この市町村への照会」を出す。

### 6.7 全ページ共通

- 最上部の固定バナー：「このサイトは平常時の課題の可視化を目的としています。災害時は必ずお住まいの自治体の公式情報に従ってください。」
- フッターに出典（国土地理院ほか）とライセンス。地図上に地理院タイルの出典表示。

- データジャーナリズム寄りの落ち着いたトーン。防災アプリ的な赤・黄の多用は避ける。

## 8. 非機能要件

- **コスト**：Cloudflare Pages / R2 / Supabase / GitHub Actions の無料枠内で動くこと。
- **パフォーマンス**：モバイル回線で地図の初期表示（LCP）2.5秒以内。初期ロードで全施設データを取得しない。
- **アクセシビリティ**：WCAG 2.2 AA。キーボード操作、色に依存しない状態表示、リスト表示。
- **出典表示**：国土地理院コンテンツ利用規約に従う。
- **公開データのライセンス**：本サービスが生成するデータは CC BY 4.0。ただし、緊急輸送道路（国土数値情報 N10、使用許諾条件「非商用」）に由来する項目（`road` の距離・路線名・区分、軸D の点数）は非商用目的に限る。N10 の線データそのもの（複製物）は再配布しない。自治体の公表値（`capacity`）は各自治体の利用条件に従い、出典を付けて配布する（`docs/DATA_NOTES.md` D-31）。
- **リポジトリ**：公開。秘密情報をコミットしない。

## 9. 実装フェーズ

### Step 0：データ調査（コードを書く前に必ず実施）

`data/raw/` の D1 CSV 2本を調べ、`docs/DATA_NOTES.md` に次を記録して**作業を止め、承認を待つ**。

1. 各ファイルの文字コード、改行、列名、行数
2. 共通IDの形式と一意性。2ファイル間で共通IDが一致する施設の有無と件数
3. 市区町村コードを導出できるか（共通IDや名称から）
4. 緯度経度の欠損、日本の範囲外の値の件数
5. 災害種別フラグの値の表現
6. 提案：`facility_id` の体系、`muni_key`、同一施設の統合規則、統合が曖昧になる件数の見込み

### Phase 1：地図に全国の避難所が出る

- プロジェクトの雛形、Lint、型チェック、テスト基盤
- `build-facilities` / `build-tiles` / `build-summaries` / `upload-r2`
- 地図（`/`）、施設詳細、リスト表示、共通バナー、出典表示
- Cloudflare Pages へのデプロイ設定
- 完了条件：公開URLで全国の施設がグレーの点で表示され、任意の施設の詳細を開ける。全国件数が D1 の行数と整合する（統合・除外の内訳を説明できる）。

### Phase 2：投稿が一周する

Supabase のスキーマと権限、認証、投稿フォーム、自動処理、モデレーション画面、異議申し立て、写真アップロード（EXIF除去→R2）、`sync-supabase`。
完了条件：投稿→承認→詳細ページに反映、までを通しで確認できる。

### Phase 3：設備が地図に出る

ビルドへの確定設備値の取り込み、軸C、表示状態の色分け、設備フィルタ（「冷房なし」）、日次ビルドの GitHub Actions 化。

### Phase 4：軸A・B・D

D3 / D4 / D5 / D6 の取り込みと各軸の算出。
