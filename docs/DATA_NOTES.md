## 2. 共通ID

### 形式

14 文字固定。両ファイルとも例外なし。

```
E 01100 00001 1 1 1
│ │     │     │ │ └ 枝番（1〜9、続きは A, B, C…）
│ │     │     │ └── 区分（避難所：1 または 2 ／ 緊急避難場所：常に 0）
│ │     │     └──── 種別（1=指定避難所、2=指定緊急避難場所）
│ │     └────────── 市区町村内の連番（5桁）
│ └──────────────── 市区町村コード（5桁）
└────────────────── 固定文字
```

以下、先頭 11 文字（`E`＋市区町村コード＋連番）を**「ID前半」**と呼ぶ。

桁の意味は公式の定義を確認したものではなく、**値の分布からの推定**。根拠は次のとおり。

- 種別の桁は、避難所ファイルで全行 `1`、緊急避難場所ファイルで全行 `2`。
- 区分の桁が `2` の避難所 10,620 行のうち 9,325 行に `受入対象者` の記入がある（「要配慮者」「高齢者」「市が特定した者」など）。`1` の 72,859 行では記入は 6 行のみ。→ **区分 2 は受入対象者を限定した避難所（いわゆる福祉避難所に相当）と推定。**
- 枝番は、同じ ID前半・同じ区分の中で重複なし。緊急避難場所ファイルに `A`〜`E` が 7 行ある（10 件目以降）。

### 一意性

- 各ファイル内で共通ID は完全に一意（重複 0）。
- **2ファイル間で共通ID が完全一致する行は 0 件。**（種別の桁が必ず違うため、原理的に一致しない）

### ID前半での対応

| | ID前半の種類数 |
|---|---|
| 指定避難所ファイル | 78,632 |
| 指定緊急避難場所ファイル | 104,390 |
| **両方に現れる** | **53,250** |
| 避難所ファイルのみ | 25,382 |
| 緊急避難場所ファイルのみ | 51,140 |

`住所同一` フラグは「相手ファイルに同じ ID前半の行があるか」とほぼ完全に一致する（避難所側：一致 83,438 行／不一致 41 行。緊急避難場所側：一致 115,799 行／不一致 125 行）。

### 重要：ID前半は「同じ住所」を表す。「同じ施設」ではない

- 同じ ID前半の行同士は、住所がほぼ必ず同じ（2ファイル間の組み合わせ 68,335 組のうち 68,303 組で住所が一致）。
- しかし施設名は違うことが多い。同じ住所に別の施設が登録されている例：
  - `E0110000238`：避難所「二条小学校」と避難所「大通・西会館」、緊急避難場所「二条小学校」
  - `E0120200043`：緊急避難場所「緑のセンター（見晴公園内）」と「見晴公園」
- 1つの ID前半に複数行あるもの：避難所ファイルで 4,238 グループ（うち施設名が全部同じなのは 1,283）、緊急避難場所ファイルで 8,422 グループ（同 39）。最大は 1 グループ 12 行。

ID前半ごとの行数の組み合わせ（避難所の行数 : 緊急避難場所の行数）：

| 組み合わせ | ID前半の数 |
|---|---|
| 1 : 1 | 44,890 |
| 1 : 0（避難所のみ） | 24,118 |
| 0 : 1（緊急避難場所のみ） | 49,523 |
| 2以上 : 0 | 1,264 |
| 0 : 2以上 | 1,617 |
| どちらかが 2 以上で両方にある | 8,360 |

### ID の安定性（未検証）

**共通ID が国土地理院の更新をまたいで変わらないかは、1回分のデータでは検証できない。**

- 安定を示唆する材料：枝番に欠番がある（避難所 1,072 グループ、緊急避難場所 1,297 グループ。例：`…201` がなく `…202` だけ存在）。削除後に詰め直していないと読める。
- ただしこれは状況証拠。次回ダウンロード時に今回分と突き合わせて確認する必要がある。そのため**今回の元データは日付付きで保管しておくことを推奨**。

## 7. 提案

### 7.1 `muni_key`

**共通ID の 2〜6 文字目（5 桁の市区町村コード）をそのまま使う。** 例：`01100`、`13101`。

- 政令指定都市は市単位になる（札幌市は 1 ファイルに 1,000 件超。JSON 1 ファイルが大きくなるが、初期ロードではなく詳細表示時に取るものなので許容範囲と見込む。サイズは Phase 1 で実測する）。
- 市町村合併でコードが変わる場合がある。`facility_id` は `muni_key` を含めない形にして、合併の影響を URL の前半だけに留める（7.2）。

### 7.2 `facility_id`

**初回採番時の「代表の共通ID」をそのまま `facility_id` とし、対応表をリポジトリで管理する。**

- 代表の選び方：統合された行のうち、避難所（区分 1）＞避難所（区分 2）＞緊急避難場所 の優先順で、枝番が最小のもの。例：`E0110000001111`。
- 対応表（共通ID → `facility_id`）を Git 管理のファイルとして持つ（置き場所の案：`data/registry/facility-ids.csv`）。再取り込みではまず対応表を引き、載っている共通ID は必ず同じ `facility_id` になる。
- これにより、あとから指定が追加・解除されても（例：緊急避難場所だけだった施設に避難所の指定が付く）ID は変わらない。対応表なしで毎回規則から計算すると、このケースで ID が変わり、市民投稿が迷子になる。
- 対応表から消えた共通ID の施設は削除せず `deprecated_at` を付ける（仕様 §5.6）。
- 前提：共通ID 自体が更新をまたいで安定であること。これは未検証（2 章）。もし不安定だった場合は、対応表のキーを「市区町村コード＋正規化した施設名＋住所」に切り替える必要があり、その時点で報告する。

### 7.3 同一施設の統合規則

統合の単位は「ID前半が同じ、かつ施設名が対応する」行の集まり。照合用の施設名は NFKC 正規化して空白を除いたもの。

| R2 | ID前半が同じ ＋ 括弧書きを除いた施設名の一方が他方を含む ＋ 距離 200m 未満（例：「西条小学校」と「西条小学校（グラウンド）」、「栃木高校」と「栃木高校【洪水時は2階以上に避難】」） | **自動統合を提案（要承認）** | 7,059 組 |

- 同じファイル内の重複らしき行（6 章の 28 行＋107 行）は、同じ施設として 1 件にまとめ、元の共通ID をすべて対応表に載せる。

### 12.5 垂直避難などの備考の調査（D-19 の案、2026-11-15）

照合が済んだ 671 市区町村・32,763 件の指定で、備考欄の書かれ方を調べた（全国分の取得の途中経過による。完了後に数字を更新する）。

| | 件数 | 割合 |
|---|---|---|
| 照合した指定 | 32,763 | |
| うち備考あり | 1,198 | 3.7% |
| 想定区域と重なった指定 | 6,184 | |
| うち備考あり | 574 | 9.3% |
| うち階数・屋上・校舎などに触れているもの | 431 | 7.0% |
| うち「使用不可」「除く」などに触れているもの | 14 | 0.2% |

**分かったこと**

- 備考は自由記述で、災害種別ごとに分かれていない。例：「洪水は２階以上、高潮、津波は３階以上が対象」（川崎市）、「洪水時：２階以上に避難」（帯広市）、「水害時は避難場所使用不可 土砂災害のおそれがある場合の避難場所は建物2階のみ」（一関市）、「荒川が氾濫するおそれがある場合は、開設しない」（台東区）。
- 重なった指定の 9 割には備考がない。**備考がないことは「条件がない」ことを意味しない**（備考欄を使っていない自治体が多い）。
- 書き方は自治体ごとにそろっている（川崎市、帯広市、佐野市など）。

**案**

1. 備考があっても判定は変えない。想定区域と重なっていれば `attention`（要確認）のまま。重なりは事実であり、備考の文章から「上の階なら適合」と機械的に読み替えることはしない（読み違えたときに、根拠のない安心を与える）。
2. 重なりがある指定に備考がある場合は、詳細ページの軸A の欄に「自治体の備考」として原文のまま並べて表示する。現在は指定の一覧の中にだけ出ていて、重なりの表示と離れている。
3. 備考を分類するフラグ（「垂直避難あり」など）は作らない。正規表現での分類は取りこぼしと誤判定があり、フラグがない施設を「条件なし」と読まれるおそれがある。
4. 現在の注記（「指定の誤りを意味するものではありません。建物の上の階への避難を前提にした指定などがあります。」）はそのまま使う。

**仕様と実データの食い違い・確認が必要な点**

1. **「2km 未満=70」は、表示状態「良好」の基準（75 以上）に届かない。** 敷地内備蓄が「あり」（+20）でなければ、500m〜2km の施設は「良好」にならない。埼玉県では指定避難所の 39% が該当する。仕様どおりなら「良好」は「道路から 500m 未満」または「2km 未満で敷地内備蓄あり」を意味する。この意味でよいかの確認が要る。
2. **高速道路は、近くにあっても出入口がなければ使えない。** 影響は小さいが、距離の計算から高速自動車国道と都市高速道路を除く案を出す。
3. **直線距離は、実際の道のりではない。** 川や線路をはさむ場合がある。算出根拠（`breakdown`）と画面に「直線距離」と明記する。
4. **敷地内備蓄が未確認の場合の扱いが仕様にない。** 加点も減点もせず、`breakdown` に「未確認」と残す案を出す（未確認を「なし」として減点しない。CLAUDE.md 絶対ルール 1）。
5. **県境の施設**は、隣の県の道路のほうが近い場合がある。全国分をまとめて最寄りを探す。
6. **資料年月が古い**（埼玉県は 2016 年）。詳細ページに、最寄りの道路の名称・区分とあわせて資料年月を表示する。
7. 区分（第 1 次・第 2 次など）は点数に使わず、`breakdown` に記録するだけにする（仕様に定めがないため）。
8. 対象は指定避難所の指定がある施設とする（SPEC §2 の「軸 B/C/D の主対象」）。緊急避難場所だけの施設は「未評価」。

**実装の案**（承認後に着手）

- 元データは `data/raw/n10/{取得日}/` に手動で置く（47 件、合計およそ 60MB の見込み。配布ページに一括ダウンロードがある）。

### 12.7 軸B（収容余力）のデータ調査（2026-11-15）

**調べたこと**：全国のオープンデータ目録（BODIK ODM）を「evacuation_space」「指定緊急避難場所」で検索し、CSV を 12 市町村分抜き取って中身を見た。

**公開の広がり**

- 目録で見つかったのは 174〜258 市区町村（検索語による）、36〜39 都道府県。全 1,726 市区町村の 1〜1.5 割にあたる。目録に載っていない自治体サイトでの公開は数えていないので、これは下限。
- 利用条件は CC BY（4.0 または 2.1 JP）が大半で、一部が公共データ利用規約（PDL1.0）。自治体ごとに出典表記が必要。

**抜き取った 12 件の中身**

- 12 件すべてに収容人数の列があり、10 件で記入されていた（969 行中 919 行）。野洲市と粟国村は列だけあって空欄。
- **有効面積の列は 1 件もなかった。** 自治体標準オープンデータセットの「指定緊急避難場所一覧」に面積の項目がないため。
- 値の書き方がそろっていない：数字だけ（京都市「1427」）、単位付き（佐賀市「429人」）、算出根拠付き（長岡京市「1,350人（3.3平方メートルあたり2人）」、宇治市「1460人（3.3平方メートルあたり1人）」）。
- **算出の前提が自治体ごとに違う。** 長岡京市は 1 人あたり約 1.65㎡、宇治市は約 3.1〜3.3㎡。根拠を書いていない自治体が大半で、同じ「収容人数」でも比べられない。
- 対象は緊急避難場所（グラウンドなどを含む）で、指定避難所の滞在スペースとは限らない（東員町は 1 施設あたり 7,670〜16,760 人）。
- 施設の ID は自治体独自の連番が多く、国土地理院の共通ID と一致しない（三重県の 2 町だけ「共通ID」の列があった）。取り込むには名称と座標での突き合わせが要る。

**仕様との食い違い**

1. **D-18 の式（有効面積 ÷ 想定収容人数）は、公開データだけでは計算できない。** 手に入るのは想定収容人数だけで、有効面積がない。
2. SPEC §3.3 の代替（収容人数だけの場合は「充足率」）も計算できない。充足率の分母になる想定避難者数は、D-18 で「推計しない」と決めたため存在しない。
3. したがって、**公開データを取り込んでも軸B は「未評価」のまま**になる。1 人あたり面積が出せるのは、算出根拠を書いている一部の自治体（長岡京市、宇治市など）と、市民投稿や施設管理者から有効面積が入った施設だけ。
4. 表示状態「良好」は軸 B・C・D がすべて評価済みであることが条件（SPEC §3.6）。**軸B が出せない限り、どの施設も「良好」にならない。**

**案**（どれも承認後に着手）

- 案 1（推奨）：軸B は点数を出さず、想定収容人数を「自治体が公表している値」として出典付きで表示するだけにする。1 人あたり面積は、有効面積と想定収容人数の両方がそろった施設にだけ参考値として出す。あわせて「良好」の条件から軸B を外すかどうかを決める。
- 案 2：仕様どおり軸B を「良好」の条件に残す。有効面積が集まるまで、全国で「良好」は 0 件のまま。
- 案 3：想定収容人数の取り込み自体を後回しにし、軸D を先に仕上げる。

取り込む場合は、目録にある自治体から順に、利用条件を確認しながら段階的に進める（自治体ごとに列名・書き方が違うため、一括では取り込めない）。

- 川越市で確認：124 施設のうち 33 件が該当。

**想定収容人数の取り込みの試行**

12.7 の調査で取得済みの 12 市町村の CSV（`data/raw/d3/2026-11-15/{市区町村コード}.csv`、Git 管理外）を使い、読み取りと施設との突き合わせを試した。`scripts/lib/capacity.ts`、`npm run data:capacity-check`（結果を表示するだけで、施設データには書き込まない）。

- 列の構成は 3 通りあった：自治体標準オープンデータセットの新しい形式（京都市、宇治市ほか）、古い形式（野洲市、出水市）、国土地理院の形式に「収容人数」「算定基準」を足したもの（三重県の 2 町。共通ID の列がある）。見出しの名前から列を探すので、どれも同じ処理で読める。

| | 行 | 人数あり | 施設に対応 |
|---|---|---|---|
| 12 市町村の合計 | 969 | 919 | 931（96%） |

- 突き合わせの規則：(1) 共通ID が一致、(2) 名称が一致して 300m 以内（複数あれば近いほう）、(3) 座標がない行は同名の施設が市区町村内に 1 つだけのとき。あいまいな行は対応づけない。
- 名称は「長岡京市立神足小学校」と「神足小学校」、「松ケ崎」と「松ヶ崎」を同じとみなす。これを入れる前は 93%（長岡京市は 27 行中 6 行）だった。
- 対応しなかった 38 行の主な原因：名称の違い（「元京都市立柏野小学校」など）、自治体側の座標の誤り（粟国村の 1 件は 6km ずれている）、国土地理院のデータにない施設。

**分かった問題（取り込み方を決める前に確認が要る）**

1. **人数は「緊急避難場所」としての値で、「指定避難所」の滞在人数とは限らない。** 東員町の校庭は 7,670〜16,760 人。同じ施設に建物と校庭の 2 行が対応し、値が食い違う例もあった（紀北町 4 施設、京都市 1 施設）。設備項目の `capacity_persons` は施設に 1 つの値なので、そのままは入らない。
2. **取り込んだ値の置き場所が未定。** 設備の確定値は Supabase の `facility_amenities` が正で、日次ビルドがそこから上書きする。公的データ由来の値を Supabase に入れるか（`confidence: official`、SPEC §4.1）、市区町村 JSON に別の項目として持つかを決める必要がある。
3. **出典と利用条件は自治体ごと。** 試した 12 件は CC BY 4.0 が 11 件、CC BY（版の記載なし）が 1 件。施設ごとに出典（自治体名、データ名、取得日）を表示する必要がある。

**案**

- 値は施設ではなく「指定」に付ける（どの行から来たか、もとの文字列、出典、取得日を一緒に持つ）。詳細ページでは「〇〇市の公表値：1,427 人（指定緊急避難場所として）」のように、何の人数かを添えて出す。
- 置き場所は市区町村 JSON（指定ごとの `capacity` 項目）とし、Supabase には入れない。市民投稿の `capacity_persons` とは別に並べて表示する。理由：公的データの再取り込みで市民投稿を失わせない（CLAUDE.md 絶対ルール 6）ことと、何の人数かが違う値を 1 つの項目に混ぜないため。
- 取り込みは、目録にある自治体から段階的に進める。対応しなかった行は一覧に出し、手で確認する。

| 小笠原諸島（A21） | 小笠原諸島振興開発特別措置法の対象市町村（面） | 2007 年 | 非商用 |
| 行政区域（N03） | 市区町村の範囲（面）。島ごとに別の面になっている | 毎年 | 版ごとに確認が要る |

- 沖縄県の離島は、上の 3 つのどれにも入らない（沖縄振興特別措置法の対象で、対応するデータを見つけていない）。
- 法律上の「離島」には、橋でつながっていて島内に緊急輸送道路がある島も含まれる。逆に、指定のない小さな島もある。

**案**

- 案 1（推奨）：行政区域（N03）の面を「ひと続きの陸地」として使う。**施設と同じ陸地に緊急輸送道路の指定が 1 本もない場合は、軸D を「未評価」にする。** 法律上の指定に頼らないので、沖縄県を含めて同じ規則で扱える。対象は、いま 10 点になっている施設（5km 以上）に限る。5km 未満の施設は、橋で渡れる場合があるので変えない。
- 案 2：A19・A20・A21 の面に入っていて、最寄りの道路がその面の外にある施設を「未評価」にする。沖縄県の離島が漏れる。
- 案 3：このままにする（5km 以上は 10 点）。

案 1 の注意点：N03 は全国で数百 MB あり、取得と前処理が要る。山間部で道路から 5km 以上ある本土の施設は、10 点のまま残る（これは仕様どおりの評価）。

### 12.18 市区町村 JSON を軽くした（2026-11-16）

**方法**

- `breakdown.logistics.road` は施設の `road` と同じ内容なので、保存時は外す。
- **内容は 1 文字も落としていない。** `shared/score.ts` の `expandBreakdown()` で元の形に戻る（テストで、戻した結果が元と完全に一致することを確認）。詳細ページの「評価の根拠を見る」は、戻した全文を表示する。
- 算出方法そのものは変えていないので、版は `phase4-4` のまま。

- 「非商用」は、出典・加工者等を表示のうえ、非商用目的のみで利用できる。**複製物の再配布はできない。**
- GIS で空間演算した結果（データベースでないもの）は、出典と加工者名を明示すれば利用できる。利用するデータがデータベースの場合は、事務局への問い合わせを求めている。
- 出典には URL と取得日を書き、加工した場合はそのことを書く。加工した情報を国が作ったかのように見せてはいけない。
- データの適用限界（空間的・時間的な誤差、欠落や古さ）を、最終利用者まで伝えること。

本サービスは N10 の線データそのものは配布していない。配布しているのは、施設ごとの最寄り道路までの距離と、その道路の路線名・区分・資料年月（空間演算の結果）。これを「非商用に限る」として扱う。

**直したもの**

- 画面下部のライセンス表記：「本サービスが生成するデータは CC BY 4.0 で提供します。ただし、緊急輸送道路に関する項目（最寄りの緊急輸送道路までの距離・路線名・区分と「到達性・兵站」の点数）は、利用条件が「非商用」の国土数値情報を加工したもので、非商用目的に限り利用できます。自治体の公表値は、それぞれの出典に記載した利用条件に従います。」
- 道路の出典表記（詳細ページ、リスト、算出根拠）：データ名・URL・取得日・加工者名（HinanBase）を入れ、利用条件が「非商用」であることを添えた。算出根拠の軸D に `license` を加えた。

**残っている点**

- 路線名・区分を施設ごとに載せることが「データベースの複製」に当たるかは、利用規約だけでは判断しきれない。気になる場合は、国土情報ダウンロードサービス事務局に問い合わせる。問い合わせるまでの間、距離だけを残して路線名・区分を外す選択もある。
- R2 の市区町村 JSON そのものには、ライセンスの記載がない（算出根拠の軸D の `license` だけ）。データダウンロード（Phase 5）で、ファイルにも利用条件を添えること。

### 12.22 想定避難者数・人口データの調査（2026-11-17、調査のみ）

**分かったこと**

1. 市区町村別の避難者数を公表している都道府県はある。ただし、機械で読める形式で公開しているのは、確認した範囲では東京都だけ。ほかは PDF の表で、取り出しに手作業か表の読み取りが要る。
2. **定義がそろっていない。** 「避難者」「避難所避難者」「避難所生活者」が混在し、時点も「1 日後」「1〜3 日目」「4 日〜1 週間後」「1 か月後」と違う。想定する地震、季節・時刻、公表年（2013〜2026 年）も都道府県ごとに違う。**都道府県をまたいで数値を比べることはできない。**
3. 対象は地震（と津波）だけ。洪水などの避難者数を市区町村別に出している例は見つからなかった。
4. 1 つの市区町村に、想定地震や条件ごとに複数の値がある（東京都は 1 区につき 24 通り）。どれを示すかの選び方自体が判断になる。
5. 全国でどこまでそろうかは、47 都道府県を調べないと分からない。

**人口データ（D6：国勢調査の地域メッシュ統計）**

- e-Stat で、500m メッシュの人口（総数・男女別）と世帯数が取得できる。2025 年 10 月から都道府県単位でも提供。
- 利用規約は政府標準利用規約（第 2.0 版）準拠で、**商用利用も可、CC BY 4.0 と互換。** 出典の記載と、加工した旨の記載が要る。
- 小さいメッシュでは一部の集計が秘匿され、隣のメッシュに合算されている（総人口は出る）。

**案**（どれも承認後に着手）

- 案 1（推奨）：**施設ごとの推定は行わない。** 規模は市区町村の単位で、公的な被害想定の避難者数を「引用」として示す。想定名、地震、条件（季節・時刻）、時点、定義（避難者／避難所避難者）、公表年、出典を必ず添える。都道府県をまたいだ比較や、全国の順位付けはしない。表示場所は市区町村のページ（Phase 5 の都道府県サマリー）。公表がない、または確認できない市区町村は「公表なし」「未確認」と書く。
- 案 1 の補足：収容人数との比較（充足の目安）は、当面出さない。比べる側の収容人数が、自治体の公表値のある 70 市区町村に限られ、しかも緊急避難場所としての人数（グラウンドを含む）が混ざっているため。
- 案 2：施設ごとに、国勢調査の周辺人口（例：半径 1km に住む人の数）を参考として出す。推定ではなく数えた事実だが、想定避難者数と取り違えられやすい。出すなら「避難してくる人数ではありません」と明記する。**今は勧めない**（案 1 で規模を示せるなら不要）。
- 案 3：本サービス独自に想定避難者数を推定する。**勧めない。** 災害想定・避難率・施設への割り当ての 3 つの仮定を重ねることになり、特に割り当ての根拠を示せない。

**次の段階**：案 1 で進めるなら、47 都道府県すべてについて、被害想定の公表年、市区町村別の避難者数の有無、定義と時点、形式、利用条件を表にする（実装はしない）。

### 13.2 照合用データの調査（位置参照情報）

- 国土交通省「位置参照情報ダウンロードサービス」の**大字・町丁目レベル**（最新は 19.0b、2025 年版）。都道府県ごとの zip に CSV（Shift_JIS）が入っている。
- 列：都道府県コード・名、市区町村コード・名、大字町丁目コード・名、緯度、経度、原典資料コード、大字・字・丁目区分コード（1=大字、2=字、3=丁目）。
- 件数と大きさ：東京都 5,389 件・CSV 0.5MB（zip 83KB）、鹿児島県 1,635 件・0.16MB。全国でも数 MB 程度の見込み。
- 利用条件：位置参照情報ダウンロードサービスコンテンツ利用規約（政府標準利用規約 第 2.0 版準拠、商用利用可、CC BY 4.0 と互換）。出典：「位置参照情報ダウンロードサービス」（国土交通省）を加工して作成。
- 番地まで持つ**街区レベル**（20.0a、2026 年版）もあるが、東京都だけで zip 3.4MB と大きく、対象は都市計画区域に限られる。今回は使わない案。

### 13.3 照合の試行

施設データの住所（東京都 3,904 件、鹿児島県 3,231 件）を、端末内で行う想定の簡単な規則（全角・半角や「ヶ・ケ」の統一、「1丁目」と「一丁目」、「本町2-3-4」を「本町二丁目」とみなす）で町丁目に照合し、施設の座標とのずれを測った。

| | 照合できた | 代表点と実際の位置のずれ（中央値 / 80% / 95%） | 照合先の内訳 |
|---|---|---|---|
| 東京都 | 97.5% | 196m / 352m / 1,160m | 丁目 3,064・大字 741 |
| 鹿児島県 | 96.0% | 873m / 1,951m / 3,714m | 丁目 408・大字 2,692 |

**分かったこと**

1. 照合できる割合は高い。照合できなかったのは、丁目の付いていない住所（「足立区綾瀬」で、データには綾瀬一丁目〜七丁目しかない）、番地と丁目の区別がつかない住所（「多摩市落合12-29」）、表記の違い（「龍郷町円」など）。
2. **農村部では大字の範囲が広く、代表点が実際の位置から 1〜4km ずれることがある。** 近くの避難所を探す機能としては大きい。都市部でも 5% は 1km 以上ずれる。
3. したがって、照合した位置をそのまま使わず、**地図上に示して、利用者が確認・調整できるようにする必要がある。**

### 13.4 仕様（2026-11-19 承認。SPEC §6.6 に反映）

**入力と照合**

- 住所（都道府県から）を入力する。端末は、その都道府県の照合用ファイル（数百 KB）だけを R2 から取得し、端末の中で照合する。サーバーには、どの都道府県を調べたかしか伝わらない。
- 候補が 1 つに決まらないとき（丁目がない、番地と区別できない）は、候補の町丁目を一覧で示して選んでもらう。
- 照合した位置を地図に示し、「この位置で合っていますか」と確認する。地図をタップして位置を直せる。照合できなかった場合も、地図で地点を選べる。
- 位置の精度は町丁目単位であることを画面に明記する。

**保存**

- 既定では保存しない。利用者が選んだ場合だけ、「自宅」「実家」などの呼び名を付けて、**その端末のブラウザ内**に保存する。保存するのは呼び名と、確認済みの位置（座標）。住所の文字列は保存しない案。
- 保存した地点は一覧から消せる。端末をまたいだ同期や、アカウントへの保存は行わない（行う場合は、住所の預かりに関するプライバシーポリシーの改定を含めて別途判断する）。

**表示**

- 近くの指定緊急避難場所と指定避難所を、直線距離の近い順に一覧と地図で示す（例：半径 3km 以内、なければ最寄りの 5 か所）。各施設の災害種別、表示状態、想定区域との重なり（軸A）、受入対象者の限定を出す。
- その市区町村の想定避難者数（12.24、公表されている都県のみ）へのリンク。
- 文言は「近くの指定避難所」にとどめる。「あなたの避難先」とは書かない。自治体が地区ごとに避難先を決めている場合があるため、自治体の公式情報（ハザードマップ、避難所の指定）を確認するよう必ず案内する。
- 直線距離であり、川・線路・崖などは考慮していないことを明記する。
- 入力した地点そのものが想定区域に入っているかは、本サービスでは調べない（ハザードタイルを取得すると、地点の周辺が外部に伝わるため）。「重ねるハザードマップで確認する」へのリンクを置き、押したときだけ位置を渡す。
- 位置を含む共有用 URL は作らない。

**データの準備**

- 位置参照情報（大字・町丁目レベル）の 47 都道府県分を `data/raw/isj/{取得日}/` に置き、ビルドで都道府県別の照合用ファイル（呼び名の正規化済み、代表点、区分）を作って R2 に上げる。施設データの更新とは別に、年 1 回取り直す。

**未決の点**

1. この機能を Phase 5（公開準備）に含めるか、別の段階にするか。
2. 近くの避難所として示す範囲（半径何 km、何か所まで）。
3. 照合用ファイルの取得を「都道府県単位」にするか（伝わる情報は都道府県だけ）、全国 1 ファイルにするか（数 MB、何も伝わらない）。
4. アドレス・ベース・レジストリ（デジタル庁）の町字マスターも候補になりうる（未調査）。表記ゆれの吸収や町字の網羅性で上回るかを比べる余地がある。

### 13.6 実装（2026-11-19）

- 照合用データ：位置参照情報 大字・町丁目レベル 19.0b の 47 都道府県分を `data/raw/isj/2026-11-19/` に取得（計 3.1MB、Git 管理外）。`npm run data:geocode` で `geocode/{都道府県コード}.json`（計 8.1MB、町丁目 191,106 件）を作る。政令指定都市の区は、市の名前で本サービスの市区町村コードに対応づけた。施設データにない 15 市町村（奥多摩町、伊勢原市、竹富町など）はコードなし（照合はできるが、市区町村ページへのリンクは出ない）。
- 施設の位置：`npm run data:points` で `points/{緯度}_{経度}.json`（106 区画、最大 1MB）を作る。日次ビルドで作り直す。
- 照合処理：`shared/geocode.ts`（端末内で動く。テスト 12 件）。丁目が書かれていない、番地と丁目の区別がつかない場合は候補を返す。町名が見つからない場合は市区町村の中心を返し、地図で選んでもらう。
- 地図：`MapAdapter` に地点を選ぶ表示（pick モード）を加えた。施設の印の上に選んだ地点を出し、タップで動かせる。
- 画面：`/near`（メニュー「住所で探す」、スマホでは「住所」）。近くの施設は 3km 以内を近い順に最初 20 件、「すべて表示」で残りを出す。3km 以内にない場合は 30km の範囲から最寄り 5 か所。
- 端末内の保存：`localStorage` の `hinanbase:places:v1` に、呼び名・座標・都道府県コード・市区町村コードだけを保存する（住所の文字列は保存しない）。読み書きに失敗しても画面は動く。

## 14. 自治体が公表している避難所の設備データの調査（2026-11-19、調査のみ）

**目的**：表示状態が「未確認」から変わらない（設備の回答率 4 割に届く施設が 0）。市民投稿を待たずに、自治体の公表データを「公的な値」（SPEC §4.1 の official）として取り込めるかを調べた。

**調べたもの**

| 調べた先 | 結果 |
|---|---|
| 全国のオープンデータ目録（BODIK ODM） | 調査時に応答なし（502）。取り込めなかった |
| e-Gov データポータル | 「避難所 設備」などで数百件当たるが、国の報告書（PDF）ばかりで、自治体の避難所ごとのデータは載っていない |
| 東京都オープンデータカタログ（区市町村を含む） | 題名に「避難所」を含むデータ 31 件。CSV の見出しを取得できた 20 件のうち、設備の列があったのは 1 件だけで、それも都の指針の数表（施設ごとの値ではない） |
| 手元の自治体 CSV 128 件（12.16 で取得した指定緊急避難場所一覧） | 設備の列は 0 件。自治体標準オープンデータセットの「指定緊急避難場所一覧」「指定避難所一覧」には、設備の項目がそもそもない |
| Web 検索 | 施設ごとの設備が分かるのは PDF の資料（名古屋市の備蓄・資機材ガイドブック、長崎市の空調整備の対象校一覧など）が中心で、機械で読める形はほぼ見つからなかった |
| 文部科学省「避難所となる公立学校施設の防災機能に関する調査」 | 都道府県別の集計（例：避難者が滞在する部屋の冷房確保 85.5%、2025 年）。体育館の空調設置は全国で約 2 割。学校ごとの値は公表されていない |

**結論**

1. **施設ごとの設備を機械で読める形で公表している自治体は、ほとんどない。** 公表データの取り込みで回答率を 4 割に上げる道は、現実的ではない。
2. 施設ごとの情報は、自治体の PDF 資料（一部の市）、施設管理者、市民の投稿に頼るしかない。
3. 都道府県・市町村単位の集計（文科省の調査など）はある。施設の値には使えないが、「この地域では避難所となる体育館の空調はまだ少ない」という背景として示すことはできる（仕様の D7、Phase 5）。

**考えられる対応（未決）**

- 案 1：表示状態の考え方を見直す。いまは設備の回答率 4 割未満なら一律「未確認」で、計算済みの軸A（想定区域との重なり）や軸D も地図の色に出ない。設備の充足度（色）とは別に、軸A の「要確認」を地図の印で常に示すなど、分かっていることを地図で伝える方法を検討する。
- 案 2：施設管理者・自治体への働きかけ。施設管理者アカウント（Phase 2 で用意済み）の利用を、自治体に案内する。自治体から設備の一覧をもらえれば、出典付きで取り込む。
- 案 3：PDF で公表している市の資料を、市ごとに手作業で取り込む。対象は限られ、更新の手間も大きい。
- 案 4：都道府県単位の集計（文科省の調査）を、地域の背景として表示する（Phase 5 の D7 を前倒し）。施設の評価には使わない。

### 14.1 案 1 の試作（2026-11-19）

- 地図の施設の印に、軸A が「要確認」（指定された災害の想定区域と地点が重なる）のとき、右上に**黒い三角に白い「!」**の印を重ねる。表示状態（色）とは独立に、設備の回答率に関係なく出す。色ではなく形で区別する。

### 14.6 ハザードのタイルの保管計画（2026-11-20）

**いま**：`data/cache/hazard-tiles/{レイヤー}/{z}/{x}/{y}.png`（取得した画像）と `….png.404`（配信元にない＝その一帯にデータがない、の目印）。運営者の Mac にだけあり、Git には入れない（`.gitignore` の `data/cache/`）。2026-11-20 時点で画像 81,301 枚・目印 98,405 件・589MB。14.5 の取得が終わると、およそ 1GB 以内の見込み。

**方針**

1. **公開する値は R2 側に残る。** 読み取った結果（軸A の `zone`、14.5 の `depth`）は市区町村 JSON に入り、R2 に公開される。毎日の再計算（GitHub Actions）は R2 の JSON を取り直して使うので、タイルは要らない。タイルが要るのは、ハザードの読み取りをやり直すときだけ。
2. **控えを 1 つ持つ。** 手元の Mac が壊れると、再取得に数時間かかり配信元に負荷をかける。取得が終わったら、`data/cache/hazard-tiles` を 1 つの圧縮ファイル（`hazard-tiles-YYYYMMDD.tar.zst`）にまとめ、**非公開**の置き場に置く。候補は Cloudflare R2 の別バケット（公開設定なし。無料枠 10GB の範囲）。いまの公開バケットには置かない（r2.dev で誰でも取れてしまうため）。→ 置き場は運営者の確認が要る。
3. **更新の周期。** ハザードマップポータルサイトのデータは、自治体の想定の見直しで随時更新される。**3 か月に 1 回**、次の順で更新する。
   - `.404` の目印を消す（新しく想定が作られた地域を拾うため）。
   - 画像は、配信元の `Last-Modified` と比べ、新しいものだけ取り直す（配信元は `ETag`・`Last-Modified` を返す。全部を取り直さない）。この仕組みはまだ作っていない（次の更新までに作る）。
   - `data:hazards` → `data:depth` → `data:rescore` 以降を流し、R2 に上げる。
   - 更新日を DATA_NOTES に記録し、画面の出典に取得日を出す（未実装）。
4. **取得の作法。** 1 秒 4 枚以内。同時接続は 12 まで（応答待ちで詰まらないようにするためで、間隔の上限は変えない）。User-Agent は汎用のもの。失敗したタイルは結果を書かない（「色なし」にしない）。
5. **消してよい条件。** 控え（2）が置けて、かつ最新の取得から読み取った結果が R2 に公開済みであること。それまでは手元のキャッシュを消さない。
